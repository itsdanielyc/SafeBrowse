# Security policy and limits

SafeBrowse is a community-built browser for reducing accidental exposure of its windows during supported recording and screen-sharing sessions. The first release is a public preview. It has not undergone an independent security audit and does not protect a compromised Windows account or certify the safety of a website.

The maintainer reports successful capture exclusion with OBS and Windows screen recording. Exact versions and capture modes were not recorded. This is not a compatibility guarantee for Google Meet, every recorder, all sharing modes, or every multi-monitor setup. Verify your own capture route with disposable content before using sensitive information. SafeBrowse does not redact other applications.

## Intended protections

The application refuses elevated or high-integrity process tokens before worker dispatch or any session-lock, clipboard, desktop, or profile changes. It hosts WebView2 under the launching user's non-elevated token, places normal sessions on a separate Win32 desktop, requests and verifies `WDA_EXCLUDEFROMCAPTURE`, separates bundled controls from remote web content, disables web messaging and host objects for website WebViews, and removes temporary profile directories after normal shutdown. Native engine events report page metadata and focus. Capture protection is enabled unless the user explicitly provides `--allow-screen-recording` and acknowledges the red warning. The override is never saved as a preference.

Website views and popups explicitly set and read back WebView2's SmartScreen requirement before navigation. View creation fails if that interface is unavailable, setting it fails, or it reads back as disabled. Windows system or enterprise policy can still override the saved value; this check does not prove that effective SmartScreen protection is enabled by the operating system.

These controls reduce some accidental exposure and isolate application UI responsibilities. They do not establish all the guarantees of a security product.

Each isolated session uses a fresh UUID desktop name, checks for a preexisting object, and retains its desktop handle. The worker must complete a bounded exchange over inherited anonymous pipes with its live parent before application desktop/profile/clipboard/UI work. The exchange checks pipe ownership, parent process identity, executable file identity, the exact worker PID, and the worker's assigned desktop. The challenge and desktop name are not command-line credentials. A supervisor-owned kill-on-close job contains the worker before it executes. Second launches fail closed instead of trusting named markers or window titles; the existing companion returns through its retained session handle.

## Known limitations

| Area | Boundary |
| --- | --- |
| Screen capture | Display affinity affects supported Windows capture APIs. It cannot prevent cameras or establish resistance to all recorders, remote access software, drivers, or malware. Microsoft explicitly states that display affinity is not a strict content-protection guarantee. |
| Alternate desktop | Desktop objects use access controls inherited from the window station. SafeBrowse does not create a separate user, restricted token, VM, or AppContainer for its host. Same-user processes with sufficient access and elevated software remain outside its protection claim. |
| Session admission | The private launch exchange removes the earlier unauthenticated worker/re-entry paths. It is not a boundary against process injection, executable tampering, or theft/duplication of process handles by same-user malware. Win32 has no documented atomic exclusive-create desktop operation; fresh unpredictable names and a preflight check are not proof against an attacker that can inspect the supervisor. The predictable single-session mutex can still be precreated to deny startup, but no longer selects another process's desktop or window. |
| Browser isolation | SafeBrowse preserves the WebView2 runtime's sandbox/isolation defaults. The host itself is not sandboxed, and this project has not demonstrated containment of browser or host-code exploits. Local runtime policies and environment overrides are not an adversary boundary. |
| On-screen keyboard | Input is delivered through document scripting rather than simulated OS keystrokes. A page can read its own fields and events. Detaching, moving or shuffling the keyboard does not protect against an observer that can read its current layout or the receiving field. This is not proof against keyloggers, malicious page scripts, mouse observers, browser compromise, or kernel-level malware. Some iframe, custom-editor, and input-method workflows are unsupported. See the [keyboard resistance assessment](docs/reviews/keyboard-resistance.md) for source evidence and proposed lab checks. |
| Profile removal | Temporary profiles use versioned ownership markers and exclusive locks. Normal shutdown retries cleanup; the next launcher scans the owned root for marked inactive profiles, with bounded work and no traversal through reparse points. Active, unrecognized and legacy profiles are skipped. Cleanup errors or scan exhaustion prevent a new session but do not guarantee eventual removal. Crashes, power loss and runtime locks can leave data behind. Deletion is not secure erasure. Persistent data, saved downloads, bookmarks and preferences are outside this cleanup. |
| Clipboard | Isolated sessions clear only the current clipboard at entry and normal exit. History, synchronization, other applications' copies, and data copied during a session are not secured. Windowed mode does not clear the clipboard. |
| Recovery | A supervisor watches for worker exit and attempts to restore Windows. The lifetime job ends the worker when its supervisor's job handle closes, but it does not restore the Windows desktop independently. An unresponsive worker, supervisor termination, system failure, or denied desktop switch can prevent automatic recovery. Windows' own Ctrl+Alt+Delete screen remains an escape route; this does not guarantee preservation of session data or profile cleanup. |
| Website trust | SafeBrowse requires and reads back the WebView2 SmartScreen setting, but Windows policy can disable effective checking despite a `true` value. There is no project-owned reputation service. HTTPS indicators describe the address scheme, not a site's legitimacy or financial safety. Phishing, account compromise, malicious pages, and server-side tracking are not solved by using a separate profile. |
| Permissions | Native requests use SafeBrowse's exact-origin permission store; choices persist separately from temporary browsing data. Permissions ask by default, with configurable popup defaults and site exceptions. Changing a rule affects future requests; reload or close the page to stop access already in use. Unknown capabilities and cross-origin frame requests for device/web API permissions are denied. Popups use the initiating frame's origin and fail closed if it cannot be identified. OS and runtime permission restrictions remain applicable. |
| Downloads | Downloads default to Ask, with saved browser-wide Disabled and Always allowed alternatives. Native deferrals hold transfers for the policy decision; WebView2 performs approved writes to a fresh Downloads/SafeBrowse/UUID directory with a sanitized filename, avoiding ordinary overwrites. Files are never opened automatically. Runtime security checks remain enabled and interrupted transfers are not resumed. Prompt metadata identifies the top-level page and native download address, not an attested initiating iframe. Pending requests are cancelled on policy changes, page navigation, tab closure or leaving the desktop. Active transfers are cancelled on navigation, tab closure, app shutdown or selecting Disabled; approved transfers may continue while returning to Windows. Saved files remain outside profile cleanup. Partial-file removal is best effort and can leave remnants. These controls do not establish that downloaded files are safe. |
| Printing | The saved Settings switch defaults to off and gates SafeBrowse's toolbar and `Ctrl+P` actions; disabled attempts point to Settings. Document-created injection additionally replaces ordinary website `window.print()` calls with in-page guidance, including when host printing is enabled. The nonconfigurable wrapper neither retains the original function nor exposes a host bridge. This is best-effort suppression, not an engine-enforced printing ban: initialization timing, fresh frame globals, retained native references, or separate browser/PDF paths can fall outside it. The current WebView2 integration has no supported global printing gate. When enabled, the host opens the system chooser for the active website and does not silently print or export PDFs. Printing requires dialog confirmation; installed destinations can include Microsoft Print to PDF. Native print, driver and save dialogs have no verified capture-exclusion guarantee, and private-desktop operation requires platform testing. Print jobs, spooler data, physical output and saved files are outside profile cleanup. |
| Compatibility | Direct file access is unavailable. Allowed popups open as tabs. Some embedded or external-application login flows may fail. Do not work around failures by disabling the browser sandbox, certificate validation, or site isolation. |

WebView2 preflight now rejects documented environment and applicable registry loader overrides, preview channels, and versions below the project's tested support floor. Created environments must report an acceptable runtime version and the intended profile directory. This detects unsupported configuration; it is not runtime binary authentication, proof of current patch status, or protection against concurrent same-user tampering. Installed updates generate a restart notice when the runtime emits its version-available event.

Native process-failure monitoring now ends the session for browser exits, failed or unresponsive renderers, failed frame renderers and unknown process failures. Outstanding requests and downloads are cancelled; pages are not automatically reloaded and submissions are not replayed. Recovery still depends on a responsive application event loop and successful Windows desktop operations. An application deadlock, supervisor termination, power loss or failed desktop switch remains outside the demonstrated recovery coverage. Check transaction status independently before retrying after failure.

The candidate workflow separates read-only verification/build jobs from its attestation job, pins actions and Rust, and requires committed source before packaging a fresh source export with hashes and build metadata. These additions have not signed or authenticated existing executables. Authenticode signing, an actual reviewed publication, independent security review and the same-user host isolation boundary remain outstanding. See [RELEASING.md](docs/RELEASING.md).

Relevant platform documentation: [Windows display affinity](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity), [desktop security and access rights](https://learn.microsoft.com/en-us/windows/win32/winstation/desktop-security-and-access-rights), [WebView2 security guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security), [SmartScreen settings and policy overrides](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2settings.isreputationcheckingrequired), [WebView2 profile storage](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/user-data-folder), and [WebView2 printing](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/print).

## Reporting a vulnerability

Use [GitHub private vulnerability reporting](https://github.com/itsdanielyc/SafeBrowse/security/advisories/new), which is enabled for this repository. Reports go privately to the repository maintainers. There is no dedicated security email address or guaranteed response-time commitment. GitHub's `users.noreply.github.com` commit address is not a reporting inbox. If the private form is unavailable, open an issue requesting a private contact without including exploit details, personal information, credentials, or recordings of sensitive content.

Provide the affected commit or version, Windows build, WebView2 version, launch options, expected versus observed behavior, and a minimal reproduction using disposable test data. Report capture-protection bypasses with the exact capture method and whether the development recording flag was enabled. Do not test against accounts, computers, or services you do not have permission to assess.

## Before a production release

Required work includes an independent architecture and implementation review (including permission, download and printing controls), a documented adversary model with verified boundaries, native interaction and capture testing across supported Windows versions, recovery and profile-removal fault testing, a reviewed update/distribution process, and review of any future external-application integration.

## Current source assessment

The [4 September 2026 remediation](docs/reviews/security-remediation-2026-09-04.md) corrects production print-wrapper wiring, adds engine failure handling, checks runtime selection, reclaims marked abandoned profiles and supplies release provenance tooling. The [preceding review](docs/reviews/security-review-2026-09-04.md) and its manifest remain evidence of the earlier source snapshot. These fixes do not establish Safepay equivalence or close the same-user malware boundary.

The [3 September 2026 source review](docs/reviews/safebrowse-security-review.md) records source remediations for the fixed-name session substitution path, direct worker launches, and elevated browser hosting. Website web messaging and host objects are disabled, and SmartScreen is explicitly required and read back before navigation. These are bounded fixes for identified weaknesses, with regression coverage described in [VALIDATION.md](docs/VALIDATION.md); they do not demonstrate resistance to an already-compromised Windows account.

The [Safepay comparison](docs/reviews/safepay-research.md) separates Bitdefender's documented claims from source-verified SafeBrowse behavior. Neither the current implementation nor these internal reviews establish security parity with Safepay. Same-user process/desktop access, recovery fault behavior, capture resistance, authenticated application distribution, and independent review remain open work before a production security claim.
