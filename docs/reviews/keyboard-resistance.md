# Keyboard and desktop resistance comparison

**Reviewed:** 3 September 2026. **Scope:** SafeBrowse's current source and primary Bitdefender/Microsoft documentation. Website reputation, malware detection, VPNs, and antivirus-suite effectiveness are outside this comparison. This is a source-and-documentation review, not an executed keylogger test or an independent audit.

## Assessment

SafeBrowse implements two of the design ideas publicly described for Safepay: a separate Windows desktop and an on-screen keyboard that delivers characters through the browser rather than generating ordinary Windows keystrokes. That supports a narrow claim about avoiding some input-observation paths. It does not establish equal resistance to keyloggers, same-user process access, browser compromise, or privileged malware.

### What the sources establish

Bitdefender's current [Safepay guide](https://www.bitdefender.com/consumer/support/answer/2051/) advertises protection against keyboard logging and screenshots, a virtual keyboard, and desktop isolation. It does not specify the current hook restrictions, desktop access-control policy, process-protection mechanisms, or host sandbox configuration necessary for an implementation-level comparison. These are vendor claims, not independently verified results here.

In an [archived Bitdefender discussion under its 2013 products](https://community.bitdefender.com/en/discussion/37584/2nd-try-safepay-keyloggers-and-screenscrapers/p1), Cristian Amarie identifies himself as Safepay's lead developer. He describes desktop-level hook separation and direct browser delivery from the virtual keyboard without Windows keyboard messages. He also acknowledges the broad capabilities of kernel-mode malware. This is useful historical design evidence; it is not a specification of the current release. Statements by other forum participants are not treated as implementation evidence.

Microsoft documents that a [global Windows hook is scoped to the calling thread's desktop](https://learn.microsoft.com/en-us/windows/win32/winmsg/about-hooks). This supports expecting an ordinary hook installed on the normal desktop to have a different scope from a SafeBrowse session. It does not establish resistance to every input-observation mechanism or prevent another process from obtaining access to the session desktop.

[Desktop security documentation](https://learn.microsoft.com/en-us/windows/win32/winstation/desktop-security-and-access-rights) states that access is checked against the desktop's security descriptor, that default ACLs come from the parent window station, and that establishing window hooks requires `DESKTOP_HOOKCONTROL`. SafeBrowse passes no explicit security attributes to `CreateDesktopW` in `src/desktop/manager.rs`; it inherits those ACLs. Its requested access mask does not define what another same-user process is denied. No verified same-user exclusion boundary follows from the desktop's separate name.

## SafeBrowse implementation and limits

| Observation path | Current implementation | Defensible conclusion |
| --- | --- | --- |
| Physical keyboard input | Normal sessions run on a separate Win32 desktop. Physical input still uses Windows and the selected input method. | Desktop hook scoping is useful, but physical typing is not converted into a protected secret-entry protocol. Other observation paths are unverified. |
| Clicked virtual characters | `src/ui/web/keyboard.html` sends a specific `KEY_INPUT` message from the bundled control. `src/ui/kiosk.rs` routes it to the selected input target. `VirtualKeyboard::generate_dom_injection_script` JSON-encodes the action and evaluates `src/keyboard/input.js`. It does not call `SendInput` or `keybd_event`. | Ordinary OS keyboard-event listeners have no generated character keystroke to observe on this path. That does not hide the click, page value, host/renderer memory, or browser-internal activity. |
| Page-side observation | `input.js` updates fields or editable ranges and emits DOM `beforeinput`/`input` events. Enter also dispatches DOM keyboard events. | A page can observe text entered into its own fields, including password fields. DOM keyboard events are distinct from OS keyboard events. Virtual input does not conceal secrets from their receiving page. |
| Static click coordinates | The rendered keyboard can shuffle letters using Web Crypto randomness. | Letter shuffling can frustrate an observer relying only on a known fixed letter arrangement. Numbers and other controls are not all shuffled. Moving a keyboard changes coordinates but does not prove protection against a listener that can observe its current layout or values. |
| Trusted control versus website | `TrustedDocument` permits only the native-supplied bundled document and `about:blank`. Website views disable web messaging and host objects in `harden_content_view`. | Websites do not receive the keyboard control's privileged application bridge. This is a separate boundary from whether they can read the text intentionally entered into them. |
| Process-level access | The host is non-elevated but runs as the launching Windows user. There is no separate host security principal or demonstrated host sandbox. | No claim of protection against sufficiently capable same-user processes, process injection, memory inspection, accessibility-based observation, elevated attackers, or kernel compromise is established. |
| ENG overlay removal | `ScopedLanguageBarGuard` changes the visibility of exact indicator classes on the session desktop. | Removing an indicator is a UI correction. It adds no keylogger protection and does not disable text services. |

Microsoft's [WebView2 security guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security) recommends minimizing native bridges and keeping the host at standard user integrity. Those measures reduce exposed privileges; they do not turn the whole host into a sandbox or make its input secret from a compromised operating system.

Capture exclusion is also a separate mechanism. SafeBrowse applies and reads back `WDA_EXCLUDEFROMCAPTURE`; the user's recorder test confirmed the intended normal-versus-debug behavior for the recorder tested. Microsoft explicitly limits [display-affinity protection](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity) to supported OS capture paths and provides no universal content-protection guarantee. It does not block keyboard logging by itself.

## Controlled verification proposal

These tests are proposed, not reported as executed. Use a disposable Windows VM snapshot with no personal accounts, credentials, shared folders, or shared clipboard. Load only a loopback test page. Do not install malware, input-monitoring drivers, or a live global keystroke logger. Keep instrumentation visible, time-bounded, and limited to test-owned windows and disposable values.

1. **Separate physical and virtual input.** A test-owned native fixture can count keyboard messages at its instrumented input target while a test page counts DOM input/keyboard events and checks a fixed dummy value. Require a working physical-key positive control at the actual target; a silent host queue is not evidence about a renderer-owned input queue. If that target cannot be instrumented without broader interception, report native observation as unavailable. Exercise physical keys and clicked virtual keys separately, including Enter, Backspace, Shift and password fields. Ordinary virtual characters should update the page without creating OS keyboard character messages. The page should still observe its own resulting value. This verifies input routing, not resistance to arbitrary global hooks.
2. **Record desktop and privilege boundaries without collecting input.** In separate standard-user and elevated lab test cases, inspect whether a disposable helper can obtain specific access rights to the fixture desktop and process. Record only access-check outcomes and token/desktop identities. Do not inject into the browser, read memory, or interpret failure to access one object as complete isolation. Kernel and hardware observers remain outside this test's claim.
3. **Check current layouts and focus.** Use disposable text to test switching tabs, closing a target, changing focus while an edit is queued, shuffled letters, keyboard movement, display scaling, and physical IME composition. Movement must not alter the trusted input route or turn a drag into a character click. Verify that the intended field receives input and another page does not.
4. **Compare like-for-like results.** If testing Safepay, record its exact product version, Windows build, privilege context and settings, and apply the same permitted fixture cases. Do not disable endpoint defenses or attempt to bypass its access controls. If the fixture cannot run equivalently, report the comparison as unavailable rather than inferring a win or parity.

Passing these cases would substantiate specific behaviors on the tested configurations. A broad keylogger-resistance claim still requires an explicit adversary model and an independent assessment of the relevant input, desktop, process and capture boundaries.
